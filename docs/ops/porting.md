# `PORTING.md` and the mechanical expression rule

`PORTING.md`, at the repository root, is the PHP → TypeScript rulebook Framework Agents port from (Story 8.2; FR-8, FR-48, AD-26). It holds the AD-26 construct mapping, the idiom table, the test-adaptation rules, the mechanical expression rule, the by-reference and exception mappings, the AD-5 frame slots, the `APP_KEY` forms, the `Promise.all` allow-list, the DIV-10 PCRE conversion rule and the generated DIV-12 pair list. It restates the spine, the PRD, the Divergence Records and the Escalation rulings; it decides nothing of its own. It is Protected (AD-16): it changes only through a Maintainer-approved Infrastructure Story.

## Check

```sh
bun run porting:check [--root <dir>]
```

`porting:check` (`tools/porting/porting.ts check`) is fail-closed. CI runs it in the required `check` job, after `divergence:check` ([ci.md](ci.md)). It reads only committed files: it never reads `conformance/upstream/`, which the `check` job does not sync. Story 8.8's Phase 1 gate reuses it as `checkPorting(root)`.

**Rules.** One violation per problem:

- `PORTING.md` exists (`PORTING.md: missing`).
- Its `##` headings, outside code fences, are exactly these, in this order: `Construct mapping (AD-26)`, `Idiom table`, `Test-adaptation rules`, `Mechanical expression rule`, `By-reference parameters`, `Exceptions`, `Frame slots (AD-5)`, `APP_KEY forms (AD-23)`, `Promise.all allow-list (AD-6)`, `PCRE conversion (DIV-10)`, `DIV-12 pair list`. A missing or out-of-order one is `PORTING.md: missing section "## <name>"`, any other is `PORTING.md: unexpected section "## <name>"`, and a required one that appears twice is `PORTING.md: duplicate section "## <name>"`.
- Every row of the spine's AD-26 table (the first cell of each row under `### AD-26` in `ARCHITECTURE-SPINE.md`) has a row in the `| PHP construct | Xaravel form | Status |` table whose first cell is character-identical and whose Status is `decided`. Otherwise it is `PORTING.md: AD-26 row "<construct>" missing` or `PORTING.md: AD-26 row "<construct>" not decided (<status>)`. A row whose first cell is not in the spine is `PORTING.md: AD-26 row "<x>" not in the spine`, a repeated row is `… duplicate`, and a row with an empty Xaravel form is `… has no Xaravel form`. When the spine has no such table, it is `<spine>: AD-26 construct table not found`.
- The region between `<!-- BEGIN div12-pairs: generated by bun run porting:generate; do not edit -->` and `<!-- END div12-pairs -->` equals the rendering of `conformance/scans/div12-pairs.jsonl`. Otherwise it is `PORTING.md: div12-pairs region drift at line <n>; run bun run porting:generate`, naming the first differing line, or the BEGIN line (or the section heading) when a marker is missing.
- `conformance/porting/expressions.jsonl` has exactly 20 lines of `{"source","mode","php","ts"}`. `mode` is `expr` or `blade`. A `<request file>#<request id>` source names a committed request under `conformance/oracle/requests/` whose `exprs`, `setup` or `template` contains `php` verbatim. An `<upstream path>:<line>` source (`framework/tests/...:<line>`, the Inventory's path form) is checked for shape only; XT-conformance-154 checks it where the snapshot is synced, which the `upstream` CI job does: it runs `porting.test.ts` after the sync ([scans.md](scans.md#ci)). An expr-mode `ts` parses as one TypeScript expression (`oxc-parser`): `(<ts>);` is one parenthesised expression statement covering the whole text, and not a comma sequence. The translator's output equals `ts`; otherwise it is `conformance/porting/expressions.jsonl:<line>: translation differs: expected <ts>, got <out>`, both JSON-quoted.

**Output.** Violations go to stderr, one per line. On success it prints `PORTING OK: <c> construct row(s) decided, <s> section(s), <r> DIV-12 pair(s), <f> fixture translation(s).`

Exit codes: 0 pass, 1 violations or any failure, 2 usage error.

## Regenerating the DIV-12 pair list

```sh
bun run porting:generate [--root <dir>]
```

`porting:generate` rewrites the region between the markers in place; the rest of the file stays byte-identical. Run it whenever `conformance/scans/div12-pairs.jsonl` changes (after `bun run scan:div12` at a new Pin). It fails when the file or a marker is missing.

The region has one row per (class, form), sorted by class and then form, with the names comma-separated and sorted, and ends with `<r> pairs in <g> groups.`. A pair's form is the first that applies:

1. `property.static !== method.static` → `no collision (static and instance sides)`.
2. `model-config` and the name is in AD-7's configuration list → `property wins; method → <renamed>()`. The renames are a constant map in the tool, from DIV-12.4: `fillable` → `setFillable`, `touches` → `isTouching`. A configuration-list name with no rename is a violation, `no AD-7 rename for <name>`, and needs an Escalation.
3. `option-pair` → `option(this, name)`.
4. Anything else → `method keeps the name; state behind Upstream's getters`.

## The translator

```sh
bun run porting:translate '<php expression>'
bun run porting:translate --blade '<blade template>'
```

`tools/porting/translate.ts` implements `PORTING.md` § Mechanical expression rule. It exports `translateExpression(php, { blade? })`, `translateBladeTemplate(src)` and `UntranslatableExpression`. It lexes with `tokenize` from `tools/scans/php.ts` and re-scans double-quoted strings itself for escapes and interpolation. It is syntax-directed: it never uses type information, and anything outside the rule table throws `UntranslatableExpression`, whose message starts with the construct (`match`, `throw`, `(array)`, `static::`, `heredoc with interpolation`, `statement`, …). The CLI prints the TypeScript and exits 0, prints `UntranslatableExpression: <construct> …` on stderr and exits 1, or exits 2 on a usage error.

## Revising the rule

The fixture comes first. To change or extend the rule:

1. Add or edit the `conformance/porting/expressions.jsonl` entry: a real Upstream input (an Oracle request, or an Upstream test file and line when no request has the construct), with the TypeScript derived by hand from the rule table, not copied from the translator. Keep exactly 20 entries; replace one if needed.
2. Change `PORTING.md`'s rule table, then `tools/porting/translate.ts`, until `bun run porting:check` passes and XT-conformance-154 covers the change.

A rule that no source states is not added locally: it goes through an Escalation (FR-114).

## Phase 1 gate

FR-8 requires `PORTING.md`, DIV-1..12 and the pilot to be on `main` before any Phase 1 Story starts (Story 8.8). The required `ownership` check enforces it (`tools/ownership/phase-gate.ts`, called by `bun tools/ownership/ownership.ts pr`; [ci.md](ci.md)). For a `story/<id>` PR whose base manifest has `epic` above 8 (Phase 0 is epics 1..8, `PHASE_0_LAST_EPIC`), it reads the base checkout, never the PR head, and fails unless it holds all of:

- `PORTING.md`, passing `checkPorting` (the rules above);
- `decisions/DIV-1.md` .. `decisions/DIV-12.md`;
- `docs/porting/pilot-report.md`, not blank;
- `decisions/PHASE-0-EXIT.md`, signed by the Maintainer.

Each unmet condition is one `phase gate:` line naming the Story, its epic, the input and its problem, ending `(FR-8, Story 8.8)`. A failing `PORTING.md` quotes its first 3 `porting:check` violations and their count. `planning/*` and `bot/*` PRs and Phase 0 Stories are never gated.

The gate holds no state. It passes for every later Phase 1 PR while `main` keeps those files. `PORTING.md` and `decisions/` are Protected Paths, and the required `check` job's `porting:check` and `divergence:check` stop a merged PR from breaking them. `docs/porting/pilot-report.md` is not Protected: a PR that removes or blanks it re-closes the gate, with a `phase gate:` line, for every later Phase 1 PR.

**Signing the Phase 0 exit.** Only the Maintainer writes `decisions/PHASE-0-EXIT.md`, at the Epic 8 checkpoint, through a `planning/*` PR. It takes the form of the `MAINT-*` rulings:

```markdown
---
decision: approved
decided_by: Maintainer
date: 2026-10-20
---

# Phase 0 exit

The Maintainer accepts Phase 0 (Epics 1 to 8) as complete; Phase 1 Stories may start.
```

The check needs `decision: approved`, `decided_by: Maintainer` (exactly), a real `date: YYYY-MM-DD`, and at least one non-blank body line that is not a heading. It checks the form of the signature, not who committed it: the orchestrator commits as the Maintainer, so the rule that only the Maintainer writes this file is a process rule.
