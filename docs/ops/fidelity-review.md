# Fidelity Review

Every Story is reviewed against Upstream by two reviewer agents, separate from the implementer (FR-111, AD-15.8, Story 8.5). Since [ESC-8.5-1](../../decisions/ESC-8.5-1.md) the review runs in the loop, in `bmad-build-auto`'s review step, not in GitHub Actions. Each verdict is recorded in the Story's spec, bound to the tree it reviewed, and `story:check`'s `approvals` clause counts them ([done-check.md](done-check.md)). No workflow calls a model, and there are no reviewer Apps, environment or API key ([identities.md](identities.md#the-fidelity-review-has-no-identity)).

## What runs

`bmad-build-auto`'s review step has a layer `fidelity-review` (`_bmad/custom/bmad-build-auto.toml`). It runs when the work is a Story with a manifest `stories/<id>.md`, or a retrospective action item from epic 9 on that changes `packages/**` (see below). It runs alongside the four adversarial layers, and runs:

```sh
bun run fidelity:review review --story <id> --spec <spec file> --loop-cli <claude|codex>
```

`tools/fidelity-review/fidelity-review.ts` builds one prompt and runs two reviewer subprocesses on it, in parallel:

| Reviewer | CLI |
| --- | --- |
| 1 | the other CLI from the loop's: Codex (`codex exec`) for a `claude -p` loop, Claude (`claude -p`) for a Codex loop. When that CLI is unavailable, the loop's CLI, with the reason recorded. |
| 2 | the loop's CLI. |

The loop's CLI is `--loop-cli`, else the env var `XARAVEL_LOOP_CLI`, else `claude` when `CLAUDECODE` is set (Claude Code sets it). Otherwise the command is a usage error (exit 2).

The binaries are `XARAVEL_FIDELITY_CLAUDE_BIN` (default `claude` on `PATH`) and `XARAVEL_FIDELITY_CODEX_BIN` (default `codex` on `PATH`, else `~/.local/bin/codex`). `XARAVEL_FIDELITY_CLAUDE_MODEL` and `XARAVEL_FIDELITY_CODEX_MODEL` pick a model (`--model`, `-m`); unset, each CLI uses its own default. With no project settings, `claude -p` defaults to a weaker model than the loop's (`claude-sonnet-5-5` when probed), so the layer prefixes the command with `XARAVEL_FIDELITY_CLAUDE_MODEL=<the loop agent's own model id>` (for example `claude-opus-5-5`) when the loop runs Claude.

Claude Code strips `CLAUDE_CODE_OAUTH_TOKEN` from the env of the commands it runs, so a `claude -p` started from inside the loop is "Not logged in". When the env has no `CLAUDE_CODE_OAUTH_TOKEN` and the file named by `XARAVEL_FIDELITY_CLAUDE_TOKEN_FILE` (default `$HOME/.claude-auth-token`, the file `tools/orchestrator/run.sh` reads) exists, the tool sets `CLAUDE_CODE_OAUTH_TOKEN` to its content, trimmed, in the claude child's env only. The token is never printed or recorded.

### Unavailable and the fallback

A CLI is unavailable only when it is:

- **not installed**: the binary is not found, or cannot be started (`ENOENT`);
- **not signed in**: its output matches `NOT_SIGNED_IN_PATTERNS` (`not logged in`, `please run /login`, `not signed in`, `please log in`/`sign in`, `run codex login`, `401 Unauthorized`, `invalid api key`, `authentication_error`, `OAuth token has expired`);
- **refusing because of a usage limit**: its output matches `USAGE_LIMIT_PATTERNS` (`usage limit`, `limit reached`, `hit your limit`, `credit balance is too low`, `exceeded your current quota`, `insufficient_quota`, `out of credits`).

The patterns are case-insensitive and are checked only on a failed run (a non-zero exit, or Claude's `is_error` result), after every copy of the prompt is removed from the output: Codex echoes its prompt, and the diff could contain those words. Only these three cases send reviewer 1 to the loop's CLI. It records `fallback: "<other> unavailable: <not installed|not signed in|usage limit>: <excerpt>"`, with an excerpt of at most 200 characters of the matching output line. When the CLI a reviewer needs is unavailable and no fallback is left, that reviewer produces no verdict.

### Isolation

Each reviewer is a fresh context that is not the implementer:

- It runs in a new empty temporary directory, never the repository, which is removed afterwards.
- Its env is allow-listed: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `TERM`, `LC_*` and `XDG_*`, plus `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY` for Claude and `CODEX_HOME` for Codex. Nothing else in the loop's env (`GH_TOKEN`, …) reaches a reviewer, so a prompt-injected reviewer has no secret to quote into the spec.
- It gets the prompt on stdin and nothing else: no project settings, no session.
  - Claude: `claude -p --output-format json --json-schema <schema> --tools "" --setting-sources "" --strict-mcp-config --disable-slash-commands --no-session-persistence --system-prompt <system>`.
  - Codex: `codex exec --sandbox read-only --skip-git-repo-check --ephemeral --color never -C <tmp> --output-schema <file> -o <file> -`, with the system text prepended to the prompt. The schema and answer files sit in a second temporary directory. Codex is **not** tool-less: it keeps a read-only sandboxed shell. Its isolation is the empty working directory, the env allow-list and the prompt's instruction to use no tool and judge only the material given.
- It answers one JSON object, validated by the CLI against the verdict schema (`verdictSchema`, which enumerates the checklist's item ids, and the prior findings' `P-<k>` ids when there are any; see [Findings of the latest reject](#findings-of-the-latest-reject)) and then by `parseVerdict`.

Each attempt has a 15-minute timeout. The child leads its own process group, and on a timeout the whole group is killed, so a descendant holding its output open cannot keep the attempt alive. A malformed answer, a timeout or any other failure is retried once on the same CLI; after that the reviewer produces no verdict. Nothing calls a model API directly or reads an API key: the CLIs use their own sign-ins.

### Finding the touched Xaravel Tests

`xaravelTestEvidence` reads the working tree. A test file is a TypeScript file under a `tests/` path segment, or a `*.test.ts`. `testUnits` splits one into top-level units: a unit starts at a column-0 line that is not `}`, `)` or `]` and that starts outside any string, template, comment, regex literal or bracket, and a comment-only unit merges into the next. A unit is an import, a declaration (`function|const|let|var|class|interface|type|enum <name>`, optionally `export`/`async`), an XT unit (it holds an `"XT-…"` literal as a call's first argument, as `xaravelTest(…)` and wrappers such as `phpTest(…)` do, or a `xaravelTest(` call) or setup (anything else).

- A changed line inside an XT unit includes it. A changed line is a non-blank added line, or, for a pure removal (a run of removed lines no non-blank added line follows), the line before it, unless that run holds only blank lines, or only blank and closing lines before a removed unit start (a whole unit removed changes no other).
- A changed declaration in a test file is a changed helper. Every declaration in the same file that uses an affected name becomes affected too, to a fixed point, and so does every name another test file imports from that file by a relative path (`import { a as b } from "./x"`, `import * as ns`). Every XT unit that uses an affected name is included.
- A changed setup unit, or a setup unit that uses an affected name (`beforeEach(() => baseRoot())`), includes every XT unit in its file.
- A helper module `…/x/index.ts` is found by its importers' `./x` too.
- A changed non-TypeScript file under `tests/` is matched by its basename: XT units and declarations whose text contains it are included or affected.
- For each included XT unit, `usedDeclarations` lists the declarations of its own file whose names its text uses, and those their text uses, to a fixed point, in file order ([ESC-9.9-4](../../conformance/escalations/ESC-9.9-4.md)). Names are matched as uses are above, so it can list more than the test needs; imported helpers and setup units (`registerClass(…)`) are not listed.

The system text is the checklist, the `## Precedence` and `## Skip Reasons and their rules` sections of `conformance/README.md` (verbatim, so F-4 does not rely on a link; the second since [ESC-14.2-5](../../conformance/escalations/ESC-14.2-5.md)) and the answering rules, plus the `addressed` rule when there are prior findings. The user text is the manifest, the Inventory rows with their Upstream lines, the Oracle requests, the patches, the evidence and, last, the section `## Findings of the latest reject (ESC-8.8-1)`.

### Findings of the latest reject

A reject stands until its findings are fixed ([ESC-8.8-1](../../decisions/ESC-8.8-1.md) item 3), so a tree change alone does not lift it: the next review must address its findings. `priorFindings(records, tree)` takes, for each reviewer slot, 1 then 2, whose last well-formed record in the spec is a `reject` on another tree, that reject's `fail` findings, item by item, then the prior findings that reject answered `fixed: false` and its items do not list again (same item, path and detail), as that slot's, numbered `P-1..P-n` across both slots. The user text lists each as `- P-<k> (reviewer <n>, F-<m>) <path>: <detail>` (on one line), or says `No earlier reject's findings to address: …` when there is none.

With prior findings, the schema also requires `addressed`, one `{id, fixed, note}` per P id, and `parseVerdict` checks it: a missing, extra or duplicate P id, a `fixed` that is not a boolean, or an empty note is a malformed answer, and so is a finding answered `fixed: false` whose item does not `fail` (`P-1 is not fixed, so F-2 must fail`). A malformed answer is retried once, then the reviewer produces no verdict. An unfixed finding therefore surfaces as its item's own `fail` findings, printed like any other. With no prior findings the schema, the system text and the answer are what they were before: no `addressed` property (a non-empty one is an extra).

## The reviewed tree

A verdict is bound to a git tree id, `reviewTree(root, mode, spec)`: the repository without the bookkeeping set [ESC-8.8-1](../../decisions/ESC-8.8-1.md) item 2 names, as Epic 8 action item 4 narrows it (only each manifest's `status:` line, the whole Story spec; the ruling lists `stories/` whole), written through a temporary index (`GIT_INDEX_FILE`), so the real index is never touched. `story:check` uses the same function, with the spec `findStorySpec` finds. A named spec must be a `.md` file under `_bmad-output/implementation-artifacts/` (resolved against the root); any other path throws `the spec <x> is not a file under _bmad-output/implementation-artifacts/`, so `--spec` cannot leave code out of the binding. The bookkeeping is:

- sprint status, `_bmad-output/implementation-artifacts/sprint-status.yaml` (`SPRINT_STATUS`), left out;
- the Story's own spec, left out whole. ESC-8.8-1 names the spec's `fidelity-verdict` records, but `bmad-build-auto` step 4 writes the rest of the spec after the review layer runs on every pass (the Review Triage Log, `review_loop_iteration`, `deferred`, `## Auto Run Result`, `followup_review_recommended`, `status: done`); binding any of that would make every Story's verdicts stale at Finalize. The reviewers never see the spec (the diff leaves out `_bmad-output/`);
- the frontmatter `status:` line of every `stories/*.md` manifest, normalised to `status: (bookkeeping)` (`normaliseManifestStatus`) rather than removed: each manifest blob is read with `git cat-file --batch`, rewritten, stored with `git hash-object -w` and put in the temporary index with `git update-index --index-info`.

Everything else is bound: the rest of each manifest (`test_ids`, `xaravel_test_ids`, `api_surface_gate`), the planning artifacts (`epics.md`, the PRD, the spine, which tools read at check time), other Stories' specs and everything else under `_bmad-output/`. Called with no spec, `reviewTree` leaves out every Story spec (`spec-<a>-<b>-*.md`); `review`, `status` and `story:check` always name one.

- Mode `worktree`: `HEAD` plus every tracked change and every untracked, non-ignored file. This is what the reviewers see, and what a verdict records. The temporary index starts as a copy of the real one with the real one's mtime (rounded down to the second), so git's racy-entry check still re-reads a file edited in the second the real index was written, and a same-size edit is never missed.
- Mode `head`: the `HEAD` commit. `story:check` counts verdicts for this tree.

So recording a verdict, a manifest status edit, a sprint status edit or finishing the Story's spec never makes a verdict stale, and a reviewed working tree committed unchanged has the same id as its head. Any other change after the review, a `test_ids` edit or an `epics.md` line included, gives a new tree, and the verdicts no longer count until the layer runs again.

Changing the binding (epic 8 action item 4) changed every tree id, so verdicts recorded before it (Stories 8.7 and 8.8) no longer count for any tree; those Stories are done and their `story:check` does not re-run.

## The verdict and its record

Each reviewer answers every item exactly once: `pass`, `fail` or `n/a`, a non-empty note, and for a `fail` at least one finding with a `path` and a `detail`. A missing, extra or duplicate id, or any malformed answer, is a malformed verdict. A verdict is `pass` when no item is `fail`, else `reject`.

Each verdict is appended to the spec, under a `## Fidelity Review` section (created at the end of the file when absent; new records go at the end of the section). A record is:

- a heading `### Reviewer <n>: <pass|reject> at tree <tree>`;
- a line naming the CLI, the model, the loop's CLI, the base, the date and any fallback reason;
- a table with one row per item (result and note), then the findings of the `fail` items only. In this Markdown, model text has every newline replaced by a space and every backtick by `'`, so it cannot open a fence or a heading, and every `@` is followed by U+200B, so it cannot mention anyone;
- when the review carried prior findings, a list of them with each answer (`- **P-<k>** (reviewer <n>, F-<m>) '<path>': <detail> **fixed|not fixed**: <note>`);
- one fenced `json` block, `{"kind":"fidelity-verdict","reviewer","verdict","tree","base","cli","model","loop_cli","fallback","date","items","prior"}`, where `prior` is the prior findings with each answer, `[{"id","reviewer","item","path","detail","fixed","note"}]` (`[]` when there were none). A record written before epic 8 action item 4 has no `prior`; that reads as `[]`, so such a record that follows a reject on another tree counts as malformed (it does not address the latest reject), not as having nothing to address. This block is the record; the rest is for reading.

The model is read from Claude's `modelUsage` keys, or Codex's `model:` header line, else the configured model, else `unknown`. Records are append-only: the tool never edits an earlier one.

## Counting

`fidelityVerdicts(records, tree)` is shared by `fidelity:review status` and `story:check`. For each reviewer slot, 1 and 2, it takes the slot's standing reject on `tree` when it has one, else the last record whose `tree` is `tree`. It passes when:

- both slots are `pass`, and
- slot 1's `cli` differs from its `loop_cli`, or its `fallback` is non-empty.

Two records from one slot are one verdict, never two.

**A Maintainer waiver** ([MAINT-2026-10-23-fidelity-waivers](../../decisions/MAINT-2026-10-23-fidelity-waivers.md), first used by [ESC-10.2-9](../../decisions/ESC-10.2-9.md)) is a third way to pass.
- **Where it lives:** an approved, current `decisions/ESC-*.md` with `decided_by: Maintainer` may carry `fidelity_waiver: { subject: "<story or item id>", items: [F-<n>, …] }`. Quote the subject: an unquoted `9.10` is the number 9.1 and grants nothing, and `escalations:check` refuses it.
- **How it counts:** for that subject, a slot's reject counts as a pass when every item it fails is waived, in one slot or both. A carried finding that is not fixed makes the next reviewer fail its item too (ESC-8.8-1 item 3). The cross-model rule still applies.
- **What still fails:** a reject that also fails an item not waived.
- **How it reads:** the count says `1 pass verdict and reviewer <n>'s reject waived by <decision> (<items>) for tree <t> (…)`, or `reviewer 1's and reviewer 2's rejects waived by …`. `review` prints `waived: <decision> (<items>)` and exits 0. On a standing reject a waiver covers, it prints `current: …` and exits 0 without running a reviewer.
- **Who writes it:** only the Maintainer. The orchestrator never does.

**An evidence gap** ([MAINT-2026-10-24-evidence-gaps](../../decisions/MAINT-2026-10-24-evidence-gaps.md)) is noted, not blocking.
- **The label:** each finding carries a `kind`, which the reviewer gives. It is `defect` when the change is wrong, or `missing-evidence` when the prompt lacks what confirms it. A recorded finding with no `kind` is a defect.
- **What counts as a pass:** a reject whose failed items are all outside F-2, F-3 and F-8, with only `missing-evidence` findings (`evidenceGapReject`), in one slot or both, beside a `pass` or a waived reject. The cross-model rule still applies.
- **How it reads:**
  - the count says `… reject noted as an evidence gap (F-<m>: missing evidence only)`;
  - `review` prints `evidence gap noted: reviewer <n> F-<m> <path>: <detail>` per finding and exits 0;
  - the spec renders the finding with _(missing evidence)_.
- **What the orchestrator does:** it lists noted gaps in the Maintainer inbox for the next retrospective, and raises no Escalation for them.
- **What never passes this way:** a fail on F-2, F-3 or F-8, whatever its kind.

**A reject stands** ([ESC-8.8-1](../../decisions/ESC-8.8-1.md)). A slot's standing reject on a tree is its last `reject` record for that tree (`standingRejects`). It stands until its findings are fixed, which changes the reviewed tree, or the evidence it asks for is supplied: a later `pass` in the same slot on the same tree never overrides it, and the count adds an item `reviewer <n>: the later pass at tree <t> (record at line <l>) does not count: the reject at line <r> stands until the reviewed tree changes (ESC-8.8-1)`. `review` refuses to re-run on that tree (see below). There is no flag to override it. Evidence a reject asks for must be supplied outside the bookkeeping paths: a change to code, tests or this tool's prompt, all in the binding tree. Evidence written in the spec, sprint status or a manifest's `status:` line changes no binding tree, so it does not lift a reject. A malformed record (bad JSON, an unknown field value, or a `verdict` that disagrees with its items) fails the count, naming the record's line. Each counted record's items are also re-validated with `parseVerdict` against the root's checklist (every id once, a non-empty note, findings on every `fail`), and its `verdict` must be the one they decide; a record that fails is malformed.

Each counted record's `prior` is re-checked too ([ESC-8.8-1](../../decisions/ESC-8.8-1.md) item 3). Its run is the contiguous records with its `tree` and `date` (one `review`'s records share both); the findings it should have addressed are `priorFindings` of the records before that run, for its tree. Its `prior` must hold each of them, with the same reviewer, item, path and detail, and no other, and pass the `addressed` rules (a finding `fixed: false` makes its item `fail`). Otherwise it is malformed: `record at line <l> does not address the findings of the latest reject before its run (ESC-8.8-1): it omits P-1 (reviewer 1, F-2) <path>: <detail>`.

## Exits and output

`review` prints one line per recorded verdict (`reviewer <n>: <pass|reject> (<cli>/<model>)`, plus `; fallback: …`), then one line per finding of a `reject`, `F-<n> <path>: <detail>`, then `NO-VERDICT reviewer <n>: <reason>` for each reviewer that produced no verdict, then `recorded <k> verdict(s) in <spec> for tree <tree>`. Retries and reviewers without a verdict are reported on stderr.

| Situation | Result |
| --- | --- |
| Each reviewer recorded `pass`, a reject a Maintainer waiver covers (prints `waived: …`), or an evidence-gap reject (prints `evidence gap noted: …`) | exit 0 |
| The spec has a standing reject for the reviewed tree | exit 1, nothing recorded, no reviewer run; stdout has `STANDING reviewer <n>: reject at tree <t>` and that reject's `F-<n> <path>: <detail>` findings, stderr says to fix them (a tree change) or supply the evidence they ask for (ESC-8.8-1) |
| A `reject` was recorded, or a reviewer produced no verdict (its record is missing; the other reviewer's is still recorded) | exit 1 |
| An empty diff, a prompt over 1,000,000 characters, a missing or invalid manifest, a missing or ambiguous spec, no base, a malformed checklist, a git error | exit 1, nothing recorded, no reviewer run |
| No `--story`, a bad Story id or option, or no loop CLI | usage message, exit 2 |

`bun run fidelity:review status --story <id> [--spec <file>]` prints `current: …` and exits 0 when the counting passes for `reviewTree(root, "worktree")`. Otherwise it exits 1 and prints `stale: …` (verdicts exist, but none for this tree) or `missing: …` (a verdict is missing, a reject, the cross-model rule, or a malformed record), with one line per slot.

### Retrospective action items

From Epic 9 on, an action item that changes `packages/**` gets the same review as a Story ([MAINT-2026-10-16](../../decisions/MAINT-2026-10-16-unattended-orchestrator.md), amendment 2026-10-22):

```sh
bun run fidelity:review review --item <action item id> --spec <the item's spec> --loop-cli <claude|codex>
bun run fidelity:review status --item <action item id> --spec <the item's spec>
```

`--item` takes an action item id, `epic-<N>-retro-item-<k>-<slug>` from a retrospective or `epic-<N>-item-<k>-<slug>` from a Maintainer ruling, and needs `--spec`. The tool reads the item from sprint status. It refuses an item that is not there, or whose `action` names no `packages/<component>` or one that does not exist. The item's scope is the paths a Story of each component its `action` names may edit. A `review` may also pass `--stale-test <path>`, repeated, for another component's test that the item's own change made stale ([MAINT-2026-10-24-stale-cross-scope-tests](../../decisions/MAINT-2026-10-24-stale-cross-scope-tests.md)). Each must be an existing file under `packages/<component>/tests/` that is not a Protected Path. It joins the scope, even for an item whose `action` names no package, and the prompt lists it as `stale_tests`. Its assigned Xaravel Test ids are the ones its own touched Xaravel Tests in that scope declare, so evidence (c) shows their Oracle fixtures, as a manifest's ids do for a Story (#326). Any other changed file is named under the diff as left out, as for a Story. The prompt shows the item's sprint status entry under `## Action item`, with a note that the checklist's "the Story" means the item. Everything else is the same as for a Story: the prompt, the reviewers, the records, the standing-reject rule and the count. `story:check` does not run for an item. The loop merges it only when `status --item` prints `current`.

## In the review step

The layer reports each `F-<n> <path>: <detail>` line and each `NO-VERDICT` line as a finding, which triage routes like any other: a `reject` returns the Story to its implementer within the same build. A standing reject's findings are reported again the same way; it is answered by fixing them, which changes the reviewed tree, never by re-running the review on the same tree.

The layer names a Finalize re-check, `bun run fidelity:review status --story <id> --spec <spec>`. `step-04-review.md` runs it before writing `status: done`. When it does not print `current` (for example because a patch changed the tree after the layer ran), the layer runs again and its findings are triaged as a new review pass. Each such re-run counts as a review loop iteration; past 5 the build halts `blocked`.

## Cost

Each run is two reviewer calls, each with up to 1,000,000 characters of prompt (roughly 250,000 to 330,000 tokens; the cap was 600,000 until [ESC-10.2-8](../../decisions/ESC-10.2-8.md)), and up to four when both are retried, plus one more when reviewer 1 falls back. They are charged to the CLIs' own plans, not to an API key. Every re-run after a tree change costs the same again.

## Limits

- **Prompt injection.** The reviewers read the diff, which the implementer wrote. Text in it could try to steer a reviewer. The prompt says the change is evidence, not instructions, and to fail when unsure; Claude has no tools and Codex only a read-only sandboxed shell it is told not to use. That lowers the risk but does not remove it. A human Code Owner still reviews Protected Path changes.
- **No live run yet.** The tests use fake CLIs. Story 8.7's pilot is the first supervised run ([ESC-8.7-1](../../decisions/ESC-8.7-1.md)); it is also where the 600,000-character cap meets the real models' context windows.
- **The patterns are a guess at the CLIs' wording.** A sign-in or usage-limit message the patterns miss is an unclassified failure: the reviewer is retried once and then produces no verdict, which fails closed. Add the new wording to the pattern constants.
- **The records are trusted as written.** They live in the Story's spec, which is not a Protected Path, and `story:check` counts what is there: an agent could append a forged record. The append-only history in the spec, under version control, is the audit trail.
- **A reject is not re-rolled.** `review` refuses to run on a tree with a standing reject, and counting never lets a later `pass` on that tree override it ([ESC-8.8-1](../../decisions/ESC-8.8-1.md)). Any change outside the bookkeeping, even one unrelated to the findings, gives a new tree and a new review, but that review sees the reject's findings and must answer each; whether a finding is fixed is the reviewer's judgement, recorded in `prior`.
- **Prior findings come from the latest record only.** Only a slot's last record is read: when the review after a reject produces no verdict in that slot, the reject is still the last record and is carried again; once a slot records a `pass` on a later tree, the earlier reject is no longer carried. A finding answered `fixed: false` is carried on by that record, as a prior finding of the next review, even when its item failed with a different finding, until a review in that slot answers it `fixed: true` or that slot records a `pass`.
- **Bound but not shown.** A change under `_bmad-output/` other than the bookkeeping (a planning artifact, another Story's spec) makes the verdicts stale, but the reviewers' diff leaves out `_bmad-output/`, so the next review does not show it.
- **Removals include no test.** Removing a whole test file, helper module or helper includes no Xaravel Test in (e): a removed file is not scanned, and a removed unit marks no other. The removal itself is in the diff.
- **A model reviewer can be wrong.** A `fail` that a human judges wrong is answered by a change (for example the evidence the reviewer asked for) and a new review of the new tree.
- **The touched-test scanner is a heuristic.** `testUnits` is a small lexer, not a TypeScript parser: a `/` after `)` is read as division, so a regex literal there can confuse it, and a top-level statement continued on a column-0 line splits into two units. Uses are matched by name in the unit's text (strings and comments included, a local that shadows a helper included), so (e) can include more tests than need it; a large shared helper can push the prompt over its cap, which stops the review. A changed import line affects nothing; re-exports, default imports and non-relative imports are not followed; a dynamic `xaravelTest(` loop is labelled with the XT literals it holds, or `(no literal XT id)`. A non-TypeScript fixture is matched by basename only.
