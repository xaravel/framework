### Diff-scope review (adversarial, edge-case, verification-gap lenses)

There is no shell injection: every spawn uses an argv array, and workflows pass matrix values through env vars.

- **R1. The Oracle image tag ignores the Dockerfile.** `imageTag` is the framework tag plus the SHA-256 of the four locks only (`tools/oracle/oracle.ts:480-496`). Story 2.6 (`9b8aeb6`) changed the Dockerfile (extension set, uid 1001) without touching the locks. So `oracle.yml#oracle` pushes different content over an existing GHCR tag, and a local `inventory` or `baseline` run can silently use a stale cached `xaravel-oracle:<tag>`. *Fix now.*
- **R2. Pin bump's "move, then regenerate" path cannot run as printed.** Three problems:
  - Move mode rewrites only the pin. The Dockerfile's `for pair in framework:13.37.0 ai:1.2.3 mcp:1.0.2 boost:2.10.3` (`conformance/oracle/Dockerfile:98`) still names the old tag, so `oracle:lock` and `oracle:build` then fail `checkDockerfile` (`oracle.ts:468-473`).
  - `REGENERATION_STEPS` (`tools/pin-bump/pin-bump.ts:55`, repeated in `docs/ops/upstream.md:44`) prints `bun run oracle:build` without its required image argument, and a bare `bun run baseline`, which is a usage error (`tools/baseline/baseline.ts:660-665`). The real baseline runs only as the CI matrix.
  - `pin-bump.test.ts:224` asserts these strings verbatim, and its fixture has no Dockerfile.

  *Fix now.*
- **R3. The GHCR write token is mounted while third-party Composer code runs.** The `oracle` job holds `packages: write` and passes `GITHUB_TOKEN` to the build (`.github/workflows/oracle.yml:64,77,101`). The Dockerfile then runs `composer install --no-progress --prefer-dist` with the token as `COMPOSER_AUTH` and no `--no-plugins`/`--no-scripts` (`Dockerfile:92-101`). The BuildKit secret keeps the token out of the image layers, but not away from plugin or script code that runs during the install. *Fix now.*
- **R4. "Two builds install the same package set" covers Composer only.** The `apt-get install` packages float with Debian (`oracle.ts:671-768`, Dockerfile). `baseline.yml` rebuilds the image in every job rather than pulling the published image by digest, so a leg's two attempts can run on different system-library builds. *Defer*: pull by digest, or pin apt.
- **R5. The PHP half of the Inventory and the baseline is never executed by `bun test`.** `lister.php`, `recorder.php` and `runner.php` are covered only by fakes and `toContain` string greps (`inventory.test.ts:131`, `baseline.test.ts:93,134,344-357`, `pest-inventory.test.ts:160`). The fork-guard bug, which recorded assertion counts 21 times, shipped and was caught only in a live CI run (`spec-2-6…md:355`). *Fix now.*
- **R6. Inventory carry-over silently drops baseline data on a malformed line.** `previousEntries` swallows parse errors (`tools/inventory/inventory.ts:624-635`), so one bad line resets every entry in that file to `assertions: null, oracle: {}`. *Fix now* (small).
- **R7. A doubly mapped test file silently takes the first Component** (`component-map.ts:271-274`). `component-map:check` runs on every PR. *Accept.*
- **R8. The test `hash` covers only the method body and dataset** (`inventory.ts:299-301`). Changes to `setUp`, helpers or attributes keep the same hash, so pin bump reports no "changed" for them. *Accept as designed*, and document it in `docs/ops/inventory.md` alongside R2.
- **R9. The pin-line rewrite drops the line's inline comment** (`pin-bump.ts:178-187`). *Accept.*
- **R10. Submodules are not modelled in the tree hash** (`tools/upstream/upstream.ts:121-150`). None of the four pinned repos has one. *Accept.*

## Action items

All owners are `orchestrator` unless marked otherwise. Items 1–7 are proposed remediation for the dev loop. Items 8 and 9 are spec reconciliations awaiting the Maintainer.

1. **Oracle image tag hashes the Dockerfile.** Include `conformance/oracle/Dockerfile` (and its dockerignore) in the `imageTag` hash, so an image change always gets a new tag (R1).
2. **Pin bump regeneration runs as printed.** Derive the Dockerfile's root-version list from `conformance/baseline-pin` (a build arg), or have move mode rewrite it. Make `REGENERATION_STEPS` and `docs/ops/upstream.md` exact, runnable commands (with the `oracle:build` image argument, and the baseline as a `baseline.yml` dispatch). Make the test use a fixture with a Dockerfile. Document the hash scope from R8 in `docs/ops/inventory.md` (R2, R8, S6).
3. **Keep the GHCR write token away from Composer code.** Run the Oracle's `composer install` with `--no-plugins --no-scripts` plus an explicit `dump-autoload`, or build with a read-only token and push from a step the build never sees. If the change alters Oracle outcomes, raise an Escalation (R3).
4. **Execute the PHP lister, recorder and runner in tests.** Add a tiny PHPUnit and Pest fixture project that `bun test` runs through `lister.php`, `recorder.php` and `runner.php` with real PHP when `php` is present, and skips otherwise (R5).
5. **Inventory carry-over fails loudly on a malformed committed line** instead of silently resetting the file's `assertions`/`oracle` (R6).
6. **File the Escalation for the `none` leg's missing services.** Upstream's memcached, DynamoDB and MySQL services are absent, so service-caused skips are recorded as Upstream skips. Rule options: tag those tests with their service, or add the services to the leg (S4).
7. **Delete the applied 2.6 attempt patches** (`spec-2-6-attempt.patch`, `spec-2-6-attempt-2.patch`) and the stale `planning/story-2.6-attempt` remote branch. Record the first scheduled `inventory` run's result, which verifies AC 2.7/1 (P3, S5).
8. **(Maintainer) Add `oracle` to AD-15's Inventory fields** in the architecture spine (S3).
9. **(Maintainer) Confirm or change the ai, mcp and boost tags** in `conformance/baseline-pin`, which 2.1 AC1 says the Maintainer records (S2).
