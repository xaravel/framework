The probes (local PHP 8.5.11, pure builtins only, no vendor code; and the port on `main` at 09f3d9fb) found that the port diverges from PHP in (b) and (c), and that no part has a fix the orchestrator may make alone:
    - **(b) non-UTF-8 `.env`.** PHP: `file_get_contents` on a Latin-1 file `A=caf\xe9\n` returns its 7 bytes, and `mb_convert_encoding(…, 'UTF-8', 'ISO-8859-1')` gives `A=café`, so `Str::utf8` with `$fileEncoding` loads it. Port: `file_get_contents(): the result splits a UTF-8 sequence, which JS cannot hold` (`TypeError`). Diverges.
    - **(c) multibyte cap in the Lexer.** PHP: for the value `str_repeat('a', 999).'é'.'b'`, the Lexer's `{1,1000}` token ends inside `é` (first token 1,000 bytes, not valid UTF-8) and the tokens rejoin to the value. With 998 `a`s both sides agree. Port: `Dotenv.parse("A=" + "a".repeat(999) + "éb")` throws `preg_match(): the result splits a UTF-8 sequence, which JS cannot hold`. Diverges.
    - (b) and (c) have one cause: a PHP string is a JS string in the runtime, so bytes that are not valid UTF-8 cannot be held. No DIV clause records that limit (DIV-9 is the value model and says nothing about strings). Any fix either gives the runtime a byte-string model (an AD-9 contract change) or yields values other than PHP's, such as a Lexer token cut back to a character boundary or a `Reader` that skips `file_get_contents`. Either way that is a new divergence, so it is outside the item.
    - **(a) nested-frame snapshot.** PHP has no frames, so the Oracle cannot decide it. AD-5 says a child unit's "reads fall through to the parent". A per-key fall-through needs the parent's overlay, but `frameOverlay` returns only the nearest frame that holds a key. So the fix needs a new `@xaravel/runtime/scope` read, a `contract` change that the 2026-10-30 amendment sends to a second key. It also needs a choice of semantics that nothing settles: when a child wrote `a.b` and the parent later writes `a`, what does the child see?
    - **(d) `class_exists` on a trait.** A stable answer needs a trait mark set when the trait is declared. Registering a trait is AD-10/AD-26's `registerClass`, and the trait files live in other components (`packages/macroable`, `packages/conditionable`, …). So it needs a Registry contract (for example `registerTrait`) and edits outside the item.
    - **Questions for the Maintainer:** (1) Should the runtime's UTF-8-only string limit become a DIV clause, and should (b) and (c) be recorded under it, or should the runtime gain byte strings? (2) For (a), should config writes fall through per key, through a new scope read? If so, which semantics, and in which Story or item? (3) For (d), should there be a declaration-time trait mark in the Registry, and with which Story? Once ruled, the item is one `planning/retro-15-*` build, or its parts move to the Stories the rulings name.
  - *Resolved (b) and (c), 2026-10-30.* The Maintainer ruled them under the new clause DIV-9.18 (`decisions/MAINT-2026-10-30-epic-15-items-2-5.md` item 2.1): the runtime throws a `TypeError` naming the UTF-8 limit.
