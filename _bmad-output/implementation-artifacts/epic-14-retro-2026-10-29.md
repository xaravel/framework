### Diff-scope review (adversarial, edge-case, verification-gap lenses)

Scope: `git diff 4f21a056..24f70a08 -- packages/collections/src packages/runtime/src` (76 files, +15,220). The three lenses ran inline rather than through `bmad-review`'s reviewer fan-out, which was too heavy for this diff. The main check was a differential one: about 8,800 generated cases ran through Upstream on PHP 8.5.11 (a PSR-4 autoloader over `conformance/upstream/framework/src`, warnings suppressed per DIV-9.17) and through the port, and their outputs were diffed. The cases covered Collection, LazyCollection, Arr and the `data_*` helpers, cross-type arguments (a LazyCollection passed into a Collection, Collections inside `Arr` / `data_get`), illegal offsets and the static constructors. The port agreed on almost everything, including every Collection-vs-LazyCollection pair tried. AD-10 (`registerClass` in every `packages/collections/src` class file) and AD-5 (locale state is in a Scope Frame slot) were checked and are clean. L1–L3 were re-probed at `24f70a08` for this document.

- **L1. A bare JS generator object becomes an empty array in `Collection` and `Arr`.** `new Collection((function* () { yield 1; yield 2 })()).all()` gives `[]`, and `Arr.from(gen)` and `collect([0]).merge(gen)` drop it in the same way; PHP iterates a Generator. The runtime disagrees with itself: `Generator[Symbol.hasInstance]` accepts a bare JS generator (`packages/runtime/src/php/Generator.ts:74`–`75`), and so do `isTraversable` (`packages/runtime/src/php/traverse.ts:22`) and `iterator_to_array`, but `Traversable` (`packages/runtime/src/php/Traversable.ts:17`) does not (`gen instanceof Generator` is `true`, `gen instanceof Traversable` is `false`). So `Arr.from`'s `items instanceof Traversable` branch (`packages/collections/src/Arr.ts:534`) misses the generator, and `toPhpArray(object)` returns `[]`. LazyCollection (14.7) recognises the same value and throws Upstream's "Generators should not be passed directly…" (`packages/collections/src/LazyCollection.ts:142`–`143`). This is a Story-boundary gap: 14.1/14.2 and 14.7 each saw only one side. *Fix now* (action item 5, `packages/runtime`, with a Xaravel Test in `packages/collections`).
- **L2. `stdClass` has no `[Symbol.for('xaravel.php.props')]` hook, so PHP `==` and `<=>` on stdClass objects are wrong.** `compareObject` returns 1 (uncomparable) when either object lacks the hook (`packages/runtime/src/php/looseEquals.ts:153`–`156`), and `packages/runtime/src/php/stdClass.ts` defines none (Collection does, `packages/collections/src/Collection.ts:247`). For `[(object)['a'=>1], (object)['a'=>1], (object)['a'=>2]]`, `contains((object)['a'=>1])` gives `false` (PHP `true`), `unique()->count()` gives 3 (PHP 2) and `max()->a` gives 1 (PHP 2); `sort`, `sortDesc`, `min` and `median` differ too. `jsonDecode` produces stdClass, so `unique()` on decoded JSON objects is also wrong (re-probe: 3 for `[{"a":1},{"a":1},{"a":2}]`). DIV-9's rule is that an object PHP compares by `==` exposes its compared properties through this hook. *Fix now* for stdClass (action item 6, `packages/runtime`). *Defer* the general case (a userland class without the hook, which PHP still compares by properties) to the Component that first compares such objects, Epic 36 (Eloquent models), as a question for that Epic's first Story.
- **L3. `LazyCollection.range` uses JS `+`, `-` and `<=`, unlike `Collection.range`, so string bounds never end.** `packages/collections/src/LazyCollection.ts:199`–`218` types `from`, `to` and `step` as `number` and loops with `current += Number(abs(step))`, while `Collection.range` (`Collection.ts:260`) takes `unknown` and calls the runtime's PHP `range()`. Re-probe: `LazyCollection.range('1', '3').take(5).all()` gives `["1","11","111","1111","11111"]`; `range('a', 'e')` gives `"a","a1","a11",…`; an unbounded `.all()` grew until the process was killed (exit 137). PHP gives `["1",2,3]` and `TypeError: Unsupported operand types: string + int`. The `Enumerable.ts:517` signature says `number`, so the two classes disagree on one contract. *Fix now* (action item 7, `packages/collections`).
  - *Waiting on the Maintainer (orchestrator, 2026-10-29).* Item 7 cannot be done inside its scope. Upstream's descending loop runs `$from -= abs($step)`, so a non-numeric bound throws `TypeError: Unsupported operand types: string - int` (re-checked on local PHP 8.5: `range('e', 'a')` gives that message, `range('a', 'e')` gives `string + int`, `range('3', '1')` gives `["3",2,1]`). `@xaravel/runtime` exports PHP `plus` and `spaceship` but no PHP `-` (`packages/runtime/src/php/arithmetic.ts` has the shared `operands(a, b, operator)` helper but no `minus`). The item's `action` names only `packages/collections`, so adding `minus` to the runtime is outside its scope (MAINT-2026-10-16, amendment 2026-10-22). Building `-` from `plus` and negation inside `packages/collections` would copy runtime semantics and rewrite the TypeError's operator there, which the cross-epic lesson on one shared implementation rules out. Needs a ruling that widens the item to `packages/runtime` (add `minus` beside `plus`, with an XT-runtime case) or a new item for it.
- **L4. Illegal-offset `TypeError`s lose PHP's operation-specific wording.** `Collection.offsetExists` (`Collection.ts:1686`–`1687`, via `items.has`) throws `Cannot access offset of type array on array`, where PHP's `isset` says `… in isset or empty`. `offsetUnset` should say `Cannot unset offset of type … on array`, and `get`, `has` and `pull` should give `array_key_exists(): Argument #1 ($key) must be a valid array offset type`. `mode()` and `countBy()` on array, object or Collection items show the same mismatch on both classes. Results and exception classes match; only the messages differ, and no Upstream test asserts them. *Defer* to Epic 20 (Support: helpers, arrays, `epics.md:4207`), whose `Arr` work is the next to exercise these paths: give `PhpArray` lookups isset, unset and `array_key_exists` error variants there, or raise an Escalation if an assertion needs one first.
