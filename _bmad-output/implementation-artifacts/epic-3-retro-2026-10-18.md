### Diff-scope review (adversarial, edge-case, verification-gap lenses)

`bmad-review` ran three lens reviewers over the code diff, excluding generated data. Findings R1–R3 were re-checked against the files at `dae7831`.

- **R1. The forked evaluator child does not buffer output.** There is no `ob_start()` in `tools/oracle/evaluate.php` (the fork is at `:436`), and stdout is inherited. Any `echo`, notice or `dump()` from Upstream code or from a request therefore lands in the line-per-request protocol that `parsePass` reads (`fixtures.ts:393-397`). That aborts the batch, and a crafted per-Story request could inject protocol lines. Two lenses found it independently. *Fix now.*
- **R2. The comment on who can read the signing key is wrong.** `oracle.yml:25-27` says `ORACLE_SIGNING_KEY` is readable by "no other job", but the `story` job, which runs under `pull_request_target`, also uses `environment: oracle` (`oracle.yml:236`). `docs/ops/oracle.md:65,201` repeats the claim. A mitigation exists: the job checks out the base SHA with `persist-credentials: false`. *Fix now* (docs). *Defer* the question of a separate per-Story key.
- **R3. Story-supplied PHP runs without resource limits.** `runInImage` runs `docker run --rm --network none` with no `--memory`, `--pids-limit` or `--cpus` (`tools/oracle/oracle.ts:725`), inside a job that holds the signing key and the App key. *Fix now.*
- **R4. A per-Story request can get arbitrary PHP signed.** `story-requests.ts:122` checks ownership of the Test ID only, and `evaluate.php:353-354` evaluates whatever `setup`/`exprs` contain. CODEOWNERS on `/conformance/oracle-requests/` (`.github/CODEOWNERS:7`) is the only guard. That is a route to weakening the grader. *Defer* into S5: tie per-Story inputs to extraction, or require a recorded reason.
- **R5. Per-Story files can go red through no change of their own.** When a later batch adds the same request, `story-requests.ts:131-138` (used by `verify.ts:81-82`) fails an already-merged file, and no Story may edit it. Cross-file duplicates resolve by sorted file name, so `10.1` takes ownership before `3.4` (`:203,224-231`). *Defer* into S5.
- **R6. Some request kinds become signed error fixtures.**
  - Pest IDs give a `fatal` (`evaluate.php:257-268`).
  - XT validation-message requests fail at `setup` (`:398-402`).
  - `input.now` is not applied for XT IDs (`:395-397`).
  - Four view fixtures hold only `{stage:fatal}`.

  *Defer* into S5.
- **R7. Small validator mismatches.** The TS validator accepts lone surrogates that PHP `json_decode` rejects, which aborts the whole run (`request.ts:8-13` vs `evaluate.php:514-516`). The batch and commit-step Component regexes differ (`fixtures.ts:229` vs `oracle.yml:334`). *Fix now* (small).
- **R8. The `workflow-permissions` gate misses write scopes granted through an App token** (`oracle.yml:316-318`, `tools/workflow-permissions/workflow-permissions.ts:19`). *Defer.*
- **R9. The scan lexer has gaps.**
  - `new readonly class` is read as a class named `extends` (`tools/scans/php.ts:713-722`).
  - `?->fn(` is not excluded (`:690-691`).
  - `${expr}` with a nested quote ends the string early (`:120-139`).

  Only one direct tokenizer test exists (`scans.test.ts:155-165`). The `--check` runs catch regressions only for constructs present in Upstream today. *Defer.*
- **R10. The tools/** exemption from AD-9 and AD-23 is not written down.** `decodeLiteral` returns `undefined` (`tools/oracle/extract/php.ts:1261`), and the canonical JSON uses `JSON.stringify` (`request.ts:113-126`, `fixtures.ts:84`). These are not framework values. *Accept*; see Open questions.
