# Epic 10 item 4: a Pipeline is a declared thenable in the async-surface tool

Action item `epic-10-item-4-async-surface` (decisions/ESC-10.2-2.md, decisions/ESC-10.2-6.md). Resumed 2026-10-23 after the Maintainer named `packages/contracts` for the item and approved the `tools/async-surface/` change inside it (ESC-10.2-2, "Route amended", #352).

<intent-contract>

## Intent

**Problem:** ESC-10.2-2 makes `Illuminate\Contracts\Pipeline\Pipeline` and `Illuminate\Pipeline\Pipeline` declared thenables, so `send`, `through` and `via` (which return `this`) must get `thenable` lines in `packages/contracts/async-surface.json`, and lint must see a Pipeline as a thenable. Today the list lacks both FQCNs, the resolver knows only `registerClass` registrations (a contract token is `contract(...)`, ESC-10.1-3), and the walk ignores a `this` return type.

**Approach:** Add both FQCNs to `THENABLE_TYPES`; teach `moduleInfoOf` (the shared resolver behind `registeredFqcn` and lint's same-file map) to read a top-level `const X = contract("<FQCN>", …)` as a registration of `X` (a `registerClass` of the same local wins); in the async-surface walk, resolve a `this` return type in a class or interface to that declaration's own FQCN. Regenerate `packages/contracts/async-surface.json`.

## Boundaries & Constraints

**Always:** Match by qualified name only (never short name). A contract token counts only when the callee is the identifier `contract` bound by a named import `contract` (any specifier) and its first argument is a string literal FQCN, after unwrapping parentheses, `as`, `satisfies` and `!` around the call; `contract<T, B>(…)` type arguments are fine. `this` resolves through the owner's local name in its own source file, so only a listed owner yields a line. ESC-10.2-6: the tool does not check a tag's reason (`TAG_VALUE` accepts `callback` on any method), so nothing changes there. Update the header comments of both files, `docs/ops/async-surface.md` and `docs/ops/lint.md`.

**Never:** Change any `packages/contracts` file except the regenerated `async-surface.json`; the contract's `then` overloads are Story 10.2's. No other package's `async-surface.json` changes. Never remove or weaken an assertion: XT-conformance-133's short-name set only gains `Pipeline`. No type-aware resolution.

## Investigation

- **The list.** The thenable list the tool reads today is `THENABLE_TYPES` in `tools/lint-rules/thenables.ts`, shared with lint's `xaravel/no-async-thenable-return`. XT-conformance-133 (`conformance/tests/xaravel/lint-signatures.test.ts:142`) pins its exact short-name set, so adding the two Pipeline FQCNs also updates that expected set (`Pipeline` added; nothing removed).
- **The list alone is not enough.** A type name is a thenable only when `registeredFqcn` resolves it to a module that calls `registerClass('<FQCN>', X)`. `Illuminate\Contracts\Pipeline\Pipeline` is a contract token (`contract(...)`), never passed to `registerClass` (ESC-10.1-3). And `send`, `through` and `via` in `packages/contracts/src/pipeline/Pipeline.ts` return `this`, which the walk does not resolve at all. For those methods to get thenable lines, as the ruling says they do, the resolver must also recognise a contract token's FQCN and treat `this` in a thenable class or interface as that thenable.
- **ESC-10.2-6's half.** The tool does not check a tag's reason: `TAG_VALUE` (`tools/async-surface/async-surface.ts:107`) accepts `callback` on any method. Per the ruling's "if" clause, nothing changes there.
