# PRD Quality Review — Xaravel

## Overall verdict
The PRD has a real, falsifiable thesis ("Laravel's own test suite is the specification"), and the Conformance System built around it gives the ~45 Upstream-Component FRs a strong, machine-checkable definition of done through the §4 Global rule. Two things are at risk. First, the public-alpha definition contradicts the phase plan: §7.2 needs work that §7.3 places in post-alpha Phase 9, and the SM-1 gate of 90% passing cannot be reached while integration tests stay gated until Phase 9. Second, the Xaravel-only half of the product (htmx, Boost, Mockery, Class Registry) has no working definition of done, and nothing in the requirements stops an unattended agent from weakening Ported Tests. Both problems can be fixed in one revision pass. Until then the PRD is not safe to hand to epic creation or to unattended Framework Agents.

## Decision-readiness — adequate
Most choices are stated as firm decisions, not as "considerations": Bun-only (FR-12), htmx as the only front end (§2.2), Strict Loading by default (DIV-2), "Cutting scope to a minimal v1" as an explicit Non-Goal (§7.1), and performance explicitly traded away (NFR-6, SM-C3). FR-41 is the model for the document. It states the decision, the mechanism and the reason ("A plain 302 would be followed silently by `fetch()` and the whole page would be swapped into the target element"). The counter-metrics in §8 show the author expected pushback on test-skipping and throughput.

The weakness is what the PRD does not flag. The PRD body has zero `[NOTE FOR PM]` callouts, although it has several unresolved structural tensions (see Strategic coherence C1–C3). The only callout in the folder (addendum line 72) is stale. Open Questions are real questions, but most have no "resolve by" gate, even though several block early Phases.

### Findings
- **[medium]** Real tensions go unflagged, and the only NOTE FOR PM is stale (PRD body; addendum §Phase-gate note) — The addendum says "Decide during epic planning whether to pull Auth forward into the alpha", but §7.2 already settled this ("This includes Auth (FR-92 to FR-95) and Queue … because the Maintainer's app needs login and background jobs"), and the memlog records the decision. Meanwhile, the open conflicts between §7.2 and §7.3, between SM-1 and FR-7, and over the integration-test gate carry no callout. *Fix:* Delete the stale addendum note. Add `[NOTE FOR PM]` at §7.2/§7.3 and SM-1 until the Strategic-coherence findings are resolved.
- **[medium]** Open Questions have no resolve-by gates, and some block early Phases (§9) — Only OQ-4 has a gate ("A spike is needed before Phase 2"). OQ-9 ("do contributors need Docker?") decides whether Framework Agents can generate Differential Tests at all, and FR-6 belongs to Phase 0. OQ-7 (`QUERY` method) blocks FR-30 in Phase 6. OQ-5 (htmx 4 on `next`) blocks FR-17 in Phase 7. OQ-8 (bcrypt over 72 bytes) blocks FR-78 in Phase 3. OQ-1 is not open: it ends "Not required, but friendly". It is an optional to-do. *Fix:* Give each OQ a "must resolve before Phase N / Story X" line and an owner. Move OQ-1 to a task list or to NFR-8.
- **[medium]** The full-framework bet has no cost and no checkpoint (§7.1, §5.3) — §7.1 rejects a minimal v1, and the brief sizes the work at 13,544 upstream test methods. But the PRD gives no timeline, no capacity assumption, and no point at which the Maintainer would re-scope if SM-2 or SM-4 trend badly. §5.3 says "Laravel 14 (expected around Q1 2027) gets its own re-sync Epic". It does not say whether the alpha ships on 13.x or waits for 14. *Fix:* Add a decision rule. For example: "if SM-2 < X% after Phase 3, re-plan scope", and "the alpha ships on 13.x; the 14 re-sync starts after the alpha".

## Substance over theater — strong
There is little furniture. Four personas (Dana, Ed, Framework Agent, App Agent), and each drives decisions. Dana carries the htmx and two-database requirements. The two agent personas justify FR-9, FR-109 and NFR-10. Ed justifies FR-5 and FR-7. The Vision could not be swapped into another PRD. The NFRs are mostly product-specific: named lint rules in NFR-3, the trademark rules in NFR-8, and NFR-6 states honestly that benchmarks are for information only. Boost is credited honestly as "modelled on `laravel/boost`", not presented as innovation.

### Findings
- **[low]** The Vision's final claim is unearned (§1) — "So it is also the framework that agents find easiest to build on." No SM measures App Agent success. SM-4 measures Framework Agents building Xaravel, not App Agents building on it. *Fix:* Drop the sentence, or add a secondary SM backed by UJ-6 (for example, a fixed set of app-bug tasks solved by App Agents using Boost).
- **[low]** FR-14's only consequence is a chore that is already done (FR-14) — "The `@xaravel` npm org is registered before the first publish". The memlog shows the org already exists. This is a task, not a testable product requirement. *Fix:* Move it to a launch checklist.

## Strategic coherence — adequate
The thesis is clear, and the sequencing mostly follows it. The Conformance System comes first as Phase 0. The Phases follow dependency order. The counter-metrics SM-C1 and SM-C2 guard the obvious ways to game SM-1 and SM-4. The MVP is coherent as a platform MVP proven by one dogfood app (SM-3). Where coherence breaks is the link between the alpha scope (§7.2), the Phases (§7.3) and the primary metric (SM-1). Read together, they cannot all be true.

### Findings
- **[critical]** The SM-1 alpha gate cannot be reached under the stated phase plan, and its denominator is undefined (§8 SM-1, §7.3 Phase 9) — The gate requires "at least 90% of Test IDs in Phase 1–8 Components pass". But §7.3 places "Testbench-gated integration tests" and the "integration-test unlock" in Phase 9, after the alpha. The brief's research (`laravel-anatomy.md`) counts 2,809 of 13,544 upstream test methods as integration tests, all of them gated on Testbench. Most belong to Phase 1–8 Components (Integration/Database alone has 888). On top of that, `php-only`, `intentional-divergence`, and `backend-unavailable:mysql|mariadb|sqlsrv` (those drivers are post-alpha per §7.2) all count as not passing. So the pass rate stays at roughly 79% or below. The gate can only be met by violating the plan or by quietly redefining the denominator. *Fix:* Choose one. (a) Pull a minimal Testbench into Phase 0–2 (the brief offers "a minimal version earlier if integration tests are pulled forward"). (b) Or restate the gate, for example: "≥90% of Phase 1–8 Test IDs that are not `php-only`, `intentional-divergence:*` or `backend-unavailable:*` pass", and show the arithmetic against the brief's counts.
- **[critical]** The alpha scope needs work that §7.3 schedules after the alpha (§7.2 vs §7.3) — §7.2 requires Boost FR-105–107 and FR-110. Boost "is built on FR-104" (MCP), and §7.3 puts MCP and "Boost (full)" in Phase 9, listed under "After the alpha". FR-107 runs the app's tests, and FR-60 / UJ-3 require "the Skeleton's test suite passes against both" databases. Both need the Testing toolkit (FR-96, FR-98 `RefreshDatabase`), which is "Testing" in Phase 9. UJ-1 needs `make:model -mfc` (FR-71), and FR-18 / FR-31 need Foundation's lifecycle and built-in middleware (`TrimStrings`, `PreventRequestsDuringMaintenance` live in `Foundation/Http/Middleware`). Yet Foundation appears only as "Foundation (full)" in Phase 9, and no earlier Phase names a Foundation slice. SM-2 also claims to validate FR-109 (Boost framework mode) "from Phase 2 onwards", but FR-109 is neither in the alpha nor before Phase 9. *Fix:* Define named slices with Phases, for example "Foundation core (lifecycle, HTTP/console kernels, generators) — Phase 6/7", "Testing core (FR-96, FR-98) — Phase 7", "MCP core + Boost alpha tools — Phase 8", "Boost framework mode (FR-109) — Phase 0/1". Then make §7.2 and §7.3 reference the same slice names.
- **[high]** The htmx Integration is scheduled before Blade, and other dependencies are also inverted (§7.3 Phases 3, 6, 7) — Phase 6 contains "the htmx 4 Integration", but FR-39 (Fragment responses), FR-40 (re-render the form Fragment), FR-42 (partial rendering), FR-35 ("HTML error Fragment") and FR-17 all need View (Blade), which is Phase 7. Likewise, FR-75's "queued listeners" (Events, Phase 3) and FR-89's "queued sending" (Mail, Phase 7) need Queue (Phase 8). An epics agent that follows §7.3 literally will produce Stories it cannot finish, or will mark them `blocked-by` without anyone noticing. *Fix:* Split the htmx Integration into request/response helpers (FR-37, FR-38, FR-41 in Phase 6) and Fragment rendering (FR-39, FR-40, FR-42 in Phase 7). Note the queued paths as expected `blocked-by:queue` in §7.3.
- **[high]** SM-1's target contradicts FR-7 and SM-5 (§8 SM-1, FR-7, §3 Conformance Rate) — The target is that the rate "never decreases at a Phase boundary". But pin bumps happen *only* at Phase boundaries (FR-7). Added Test IDs enter the denominator at once, because "the denominator always includes tests that haven't been ported yet". SM-5 requires those bumps. So by design, every bump that adds tests breaks SM-1 at exactly the moment it is measured, and it gives agents and the Maintainer a reason to delay bumps. *Fix:* Measure SM-1 at a fixed Pin. For example: "the rate at the outgoing Pin never decreases, and the rate after a bump is reported separately".
- **[low]** SM-4 has no target, and SM-5's unit doesn't make sense (§8) — "never more than one Phase behind the latest Laravel 13.x" mixes a work unit with a release unit. *Fix:* Change SM-5 to "the Pin is bumped to the latest 13.x tag at every Phase boundary". Give SM-4 a target, or label it tracking-only, as SM-6 effectively is.

## Done-ness clarity — thin
The two halves of the PRD are very different. For Upstream Components, done-ness is strong. The Global rule ("every Test ID of that Component is passing, or carries a Skip Reason other than `not-ported-yet`") plus the Ratchet plus Differential Tests against the Oracle is a better acceptance mechanism than most PRDs have, and it explains why FRs like FR-29, FR-56 and FR-61 can safely list no consequences. The Xaravel-only half has no Oracle and no Test IDs to fall back on: htmx (FR-37–43), Boost (FR-105–110), Installer and Skeleton, Mockery, Class Registry, the REPL, browser tests and the Conformance System itself. That half is where the PRD's differentiation lives and where unattended agents will improvise. It is underspecified, and the definition of "done" does not even apply to it. The conformance machinery also leaves its own guard rail undefined.

### Findings
- **[high]** The definition of a done Story is vacuous for Xaravel Components (§3 Story, NFR-10) — "It is done when all of its assigned Test IDs pass, or carry a Skip Reason". A Story for FR-40 or FR-106 has no Test IDs, so it is done trivially. NFR-10 promises a "machine-readable" acceptance check for every Story, but the PRD gives no source for one outside the Test Inventory. *Fix:* Extend the definition: "…or, for Xaravel Components, every acceptance Xaravel Test derived from the FR's consequences passes". Require every Xaravel-Component FR to carry numbered, individually testable consequences (for example FR-40.1, FR-40.2) that Stories can be assigned.
- **[high]** FR-40 and FR-42 name outcomes without the mechanism, so agents will invent one (FR-40, FR-42, UJ-2) — FR-40 says the framework "re-renders the current form Fragment with errors". On a POST, the framework does not know which view and data rendered the form, or which Fragment is "current". UJ-2 implies a convention (`@fragment('form')`) that no FR states. FR-42's "only the content area" is undefined. It has no consequences, says nothing about how it interacts with an explicit `.fragment()` (FR-39), and says nothing about a view that declares no content area. *Fix:* State the resolution rules. For example, the Form Request declares `fragment = ['invoices.create', 'form']`, otherwise the request fails with a named error. Define "content area" as a named section (for example `@yield('content')`) with a full-page fallback. Add testable consequences for each case.
- **[high]** No FR defines the guard against test weakening (UJ-4 step 3, SM-C1, FR-2, FR-4) — UJ-4 says "two adversarial reviewers check that the tests still match upstream", and SM-C1 depends on it ("The adversarial fidelity review rejects weakened tests"). But no FR defines that review, what it takes as input, or a mechanical check. FR-2 checks only that the label exists. FR-4 checks only that Expectations changes "appear in the change under review". An unattended agent can delete assertions from a Ported Test, or move a Test ID to `fail-known` or `php-only`, and CI stays green. This is the central failure mode of agent-built conformance work. *Fix:* Add an FR "Ported Test fidelity". It should cover: an assertion inventory per Test ID extracted from Upstream (count and kind), with CI flagging a Ported Test that has fewer assertions than its Upstream source; a mandatory fidelity review for any diff to a Ported Test; and Maintainer-visible sign-off for every move to `skip` or `fail-known`.
- **[high]** The Test ID scheme cannot identify 3 of the 4 inventory sources (§3 Test ID, FR-1) — Test IDs take the form `<FQCN>::<method>#<dataset>`. FR-1 covers `laravel/ai`, `laravel/mcp` and `laravel/boost`, and the brief addendum (line 60) says each of those has "its own Pest suite". Pest tests are closures with `describe`/`it` names, not class methods, so FR-1's "exactly one Test ID" and "identical result" consequences can't be met for them as written. *Fix:* Define a second Test ID form for Pest, for example `<file>::<describe> > <it>#<dataset>`, and state how it stays stable across pin bumps.
- **[medium]** `fail-known` has no defined role (§3 Expectations File, Story, §4 Global rule) — It is a valid status, but neither the definition of a done Story nor the Global rule mentions it, and it needs no reason. It is unclear whether an Epic can be accepted with `fail-known` Test IDs, and whether they count as Skips in the dashboard. *Fix:* State its role. For example: "`fail-known` requires a linked issue, blocks Epic acceptance unless the Maintainer waives it, and is counted separately on the dashboard".
- **[medium]** Mockery and the PHPUnit-style matchers have no boundary, though they come before almost every Ported Test (FR-100, §7.3 Phase 0) — The brief counts Mockery in 226 test files. FR-100 says "a Mockery-compatible API" with one consequence. The "PHPUnit-style matchers" appear only in §7.3, with no FR. A Phase 0 agent cannot know when either is finished. *Fix:* Add the matchers FR. Define both as "every Mockery / PHPUnit assertion API used by the Upstream test suite at the Baseline Pin", listed by a scan that runs as part of FR-1, with a coverage check in CI.
- **[medium]** FR-88's capture rule conflicts with JS module scope (FR-88, DIV-4) — "A closure that captures outer variables fails at dispatch time." In TypeScript, imported bindings (`User`, `Mail`) are outer variables, so taken literally the rule rejects almost every useful closure. The PRD also doesn't say how the worker resolves imports when it evaluates the shipped source. *Fix:* State which references are allowed (for example, module imports resolved through the Class Registry or an allowlist) and how detection works (for example, static free-variable analysis of the function source).
- **[medium]** Several Xaravel-only FRs have no testable consequences (FR-37, FR-43, FR-73, FR-106, FR-108, FR-102) — FR-37 lists accessors but not their values or formats (for example, what `requestType()` returns, and the htmx 4 shape of `HX-Target` behind `target()`). FR-43 (SSE, `multipart/mixed`, WebSocket upgrades) has none. FR-73 has none, and `tinker` is not in the Test Inventory (FR-1 covers only framework/ai/mcp/boost), so the Global rule doesn't cover it either. FR-106 has no output contract for an App Agent to rely on. FR-102 is modelled on Pest 4, which is also outside the inventory. *Fix:* Add at least one verifiable consequence to each, for example "FR-43: an SSE response flushes each event before the handler's next await, and a WebSocket upgrade on a route returns 101".
- **[medium]** Lists that claim to be complete compete with the Global rule (FR-71, FR-44) — FR-71: "The full set is model, controller, … trait". Upstream also has `make:channel` (Broadcasting, FR-91, is in scope), and the `make:queue-table` / `make:session-table` / `make:cache-table` / `make:notifications-table` commands that the `database` drivers in FR-33, FR-74, FR-85 and FR-90 need. An agent will treat "full set" as the contract. *Fix:* Rephrase as "every `make:*` command in Upstream at the Baseline Pin, including…", and do the same for directive lists (FR-44).
- **[medium]** Two NFRs give adjectives without bounds or gates (NFR-4, NFR-9) — NFR-4 says "under concurrent load", without saying how many concurrent requests or which interleavings. NFR-9's per-Component documentation has no deadline, and §7.2 doesn't require docs for a *public* alpha, even though FR-108 ships a search index over those docs. *Fix:* Give NFR-4 a concrete harness (for example "N ≥ 100 concurrent requests with randomized await interleaving per isolation test"). Add "docs for every alpha Component" to §7.2.
- **[low]** "Changed Test IDs" and the "sample" are undefined (FR-7, FR-9) — FR-7 doesn't say how a change is detected (a hash of the test method and its data provider?). FR-9's fast-mode sample has no size and no seed, despite NFR-7's determinism rule. *Fix:* Define both in one line each.

## Scope honesty — adequate
The Non-Goals (§7.1) do real work. They are specific, they name what is deferred and where (OQ-6), and they explicitly reject a minimal v1. Post-alpha items are listed. The interop decisions (FR-77, FR-78) are stated as in scope and not left as implications. The gaps are in how deferral is *mechanized*: skipped work can stay skipped without anyone noticing, and two Skip Reasons are free escape hatches.

### Findings
- **[medium]** Integration-test gating has no Skip Reason and no way to re-activate blocked tests (§7.3 Phase 9, §3 Skip Reason, FR-4) — The PRD never says which Skip Reason Testbench-gated Test IDs carry in Phases 1–8 (`blocked-by:testbench`?). More generally, a `blocked-by:<component>` Test ID is skipped, so the Ratchet never sees an "unexpected pass" when its blocker lands. Blocked tests stay blocked until someone remembers them. *Fix:* Add an FR: "when an Epic for Component C is accepted, every `blocked-by:C` Test ID is re-run, and each one that passes or fails becomes a backlog Story", and show the count on the dashboard.
- **[medium]** `php-only` and `out-of-scope:<non-goal>` need no evidence (FR-3, §7.1) — FR-3 validates `intentional-divergence:<DIV-N>` against a record, but `php-only` needs nothing, and `out-of-scope:<non-goal>` points at Non-Goals that have no IDs. These are the cheapest ways to raise SM-1 that SM-C1 warns against. *Fix:* Give Non-Goals IDs (NG-N) and validate them in FR-3. Require a one-line justification per `php-only` entry, surfaced on the dashboard.
- **[low]** Some runtime premises are not tagged (FR-84, FR-12) — Temporal, `QUERY` and bcrypt each get an OQ, but FR-84's dependence on `Bun.Image` with Laravel's Image API has no OQ or assumption tag. *Fix:* Add an OQ or cite the deps-map evidence inline.

## Downstream usability — adequate
For a chain-top PRD this is mostly well built. The Glossary is thorough and used consistently (Fragment, htmx Request, IO Terminal and Ratchet are all used exactly as defined). FR, UJ, NFR, DIV, OQ and SM IDs are contiguous and unique. Features carry "Realizes UJ-N" back-links. The gaps are the lookups that architecture and epic agents will need first.

### Findings
- **[medium]** There is no FR → Component → Package → Phase map (§4, §7.3) — Many FRs name no Component (FR-20, FR-21, FR-27, FR-29), and the htmx Integration's Package name is never given (the addendum sketch has `htmx/`). FR-22's Class Registry has no owner: it is neither an Upstream Component nor in the Glossary's list of Xaravel Components. An epics agent has to rebuild the map by inference, which is how the inversions in C2 and C3 would slip through. *Fix:* Add a table in §7.3 or the addendum: FR range → Component → `@xaravel/<pkg>` → Phase.
- **[medium]** The parity rule has no category for additions (§5.1) — "Any other difference is a bug." The PRD itself adds APIs to Upstream classes: `request.htmx()` and the related accessors (FR-37), `.hxRedirect()` (FR-41), `validateSync()` (FR-52), `await model.relation('posts')` (FR-63), and `assertHxTrigger` (FR-96). An agent that applies §5.1 strictly cannot tell whether these are allowed, or where new ones may go. *Fix:* Add §5.3 "Extensions (EXT-N)", listing every Xaravel-only API on an Upstream surface, and allow only those.
- **[medium]** DIV-1's split between sync and async is ambiguous for state that is loaded once (DIV-1, FR-28) — DIV-1 lists "sessions" and "cache" as IO, but FR-28 makes request input sync "because the body is parsed once before the middleware pipeline". Session data after `StartSession`, `old()`, `@error` and `Auth.user()` fit the same pattern, but no rule says so. Getting this wrong touches thousands of Ported Tests. *Fix:* State the general rule in DIV-1 ("data loaded by middleware is read synchronously; only fetches are IO Terminals"), and require PORTING.md's idiom table (FR-8) to classify each case.

## Shape fit — strong
The shape matches the product. This is a technical capability spec for a framework, and the PRD treats it as one: FRs grouped by Component, an explicit public-API contract with numbered divergences, and NFRs about determinism and agent operability rather than UX adjectives. The UJs are not decoration. The protagonists are developers, the Maintainer and agents, which is correct for a framework built and used by agents. UJ-4, UJ-5 and UJ-7 specify the build process itself, which is the right call for a PRD whose builders are unattended agents. No findings.

## Mechanical notes
- **ID continuity:** FR-1 to FR-110 are contiguous and unique. UJ-1–7, NFR-1–10, DIV-1–8, OQ-1–10, SM-1–6 and SM-C1–C4 are all clean. All cross-references resolve.
- **Glossary drift:**
  - §3 "Phase: one of nine groups" vs §7.3's Phase 0 and SM-2's "Phases 0–1": that makes ten.
  - Lowercase "components" means Blade components in FR-45 and FR-47, which collides with the Glossary term Component.
  - "Package developers" (FR-101) is not a defined actor.
  - "public alpha" is used throughout but defined only in §7.2. Add it to the Glossary.
- **Stale addendum references:**
  - The API table says `bun artisan` is "CLI name pending OQ-1", but OQ-1 is now about a blessing from Laravel Holdings, and §3 and the Assumptions Index confirm the name.
  - The Phase-gate `[NOTE FOR PM]` is already resolved (see Decision-readiness).
- **Assumptions Index roundtrip:** No inline `[ASSUMPTION]` tags remain. The memlog records that all ~20 were confirmed. So §10 is really a log of confirmed decisions, and the roundtrip passes trivially. Consider renaming it "Confirmed Assumptions". FR-41's entry is phrased as a rationale, not as an assumption.
- **UJ standalone-ness:** UJ-2 and UJ-3 have no "Persona + context" line and rely on UJ-1 to introduce Dana. Add one line each so they can be pulled out alone.
- **SM-1 "Validates: FR-1 to FR-5":** SM-1 measures parity for the whole framework, not the dashboard machinery. Consider "Validates: the thesis (§1)".
