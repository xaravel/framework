# Fidelity Review checklist

Two reviewer agents, separate from the implementer, review every Story against Upstream (FR-111, AD-15.8). They run in the Story's own review step, in `bmad-build-auto`, not on GitHub ([ESC-8.5-1](../../decisions/ESC-8.5-1.md)). Each reviewer is a fresh context that holds only the Story's diff, this checklist and the inputs the items name; neither is the implementing agent. At least one reviewer runs on the other agent CLI from the loop's (Codex for a `claude -p` loop, `claude -p` for a Codex loop). When that CLI is not installed, not signed in or refuses because of a usage limit, the reviewer runs on the loop's CLI and its verdict records the reason. `bun run fidelity:review` (`tools/fidelity-review/fidelity-review.ts`, [docs/ops/fidelity-review.md](../../docs/ops/fidelity-review.md)) reads this file at run time. Each item below is one `### F-<n>: <title>` heading; there is no second copy.

**Verdict rule.** The reviewer judges only the material in the prompt and answers every item exactly once with `pass`, `fail` or `n/a`, and a note saying what it compared. A `fail` lists its findings, each with a repository path and a detail the implementer can act on. When unsure, the answer is `fail`; when the evidence an item needs is missing from the prompt, the answer is `fail` with a finding that names the missing evidence. The verdict is `pass` only when every item is `pass` or `n/a`; any `fail` makes it `reject`. Each verdict, with its findings, is recorded in the Story's spec, bound to the tree it reviewed, and recording it or editing bookkeeping (sprint status, the Story's spec, a manifest's `status:` line) does not change that tree; any other edit, a manifest's `test_ids` or a planning artifact included, does. A `reject` returns the Story to its implementer within the same build. It stands until its findings are fixed, which changes the reviewed tree, or the evidence it asks for is supplied in code, tests or the review tool; re-running the review on the same tree to get a different verdict is not allowed ([ESC-8.8-1](../../decisions/ESC-8.8-1.md)). `story:check` passes the Fidelity Review only when both reviewers' verdicts on the Story's head tree are `pass`, and the cross-model reviewer ran on the other CLI or recorded why it fell back.

**Evidence notes.** The paragraphs from here to the checklist items say what the prompt carries. An item's **Check.** says only what passes and what fails; it never describes the prompt.

**Decision records.** The prompt carries, in full, every decision record (`decisions/<name>.md`) that an added line, a touched Xaravel Test, or a docblock that evidence (g) lists for a changed `packages/<name>/src/` file cites (evidence (f), [ESC-9.2-1](../escalations/ESC-9.2-1.md), [ESC-9.10-1](../escalations/ESC-9.10-1.md)). A ruling cited there is recorded evidence for any item: the reviewer checks the change against the decision's text, and does not require the citation to appear in the Story's manifest as well.

**Oracle fixtures.** The prompt lists each assigned committed request's error fixture with its error, and names each one that is present, verifies against `oracle.pub` and is not an error (evidence (c), [ESC-9.8-2](../escalations/ESC-9.8-2.md)). A fixture named there is present, even when an earlier change merged it and it is not in this diff. For each id a touched Xaravel Test declares, the prompt also shows the committed request and its fixture's output in full, when the fixture is present, verifies and is not an error. One too large for the prompt is shown with its output in a compact form that loses nothing, as its heading says: an int is its bare decimal and an array whose keys are 0..n-1 in order is a JSON array of its values. One still too large is named as omitted for size.

**Framework source.** Whenever the change touches a `packages/<name>/src/` file, the prompt carries the `@asyncRoot` rules F-9 applies: AD-6's Derivation and Enforcement rules, DIV-1 and ESC-6.4-1 (evidence (d), [ESC-9.2-2](../escalations/ESC-9.2-2.md)). For the parts of such a file the diff's hunks leave out, evidence (g) lists every top-level and documented declaration with its line, full docblock and signature, and the line of every `@asyncRoot` tag the file holds after the change ([ESC-9.3-2](../escalations/ESC-9.3-2.md)).

**Cited rules.** When an added line or a changed source file's docblock cites a bare `AD-<n>` and names one of its Rule bullets by its lead, such as "AD-5, the spine's Lifecycle", the prompt carries that bullet from the architecture spine with the consequences (evidence (b), [ESC-10.2-7](../escalations/ESC-10.2-7.md)).

**Whole files.** The prompt also shows every file the change adds or modifies in full, every decision and DIV record those files cite anywhere, the repository files they import, and the repository files a changed test file reads as data or copies into a fixture (a data file over the one-file limit as the lines the test's string literals select, as its heading says; [ESC-10.1-5](../../decisions/ESC-10.1-5.md), [ESC-10.2-7](../escalations/ESC-10.2-7.md)). When a changed test reads Upstream sources from the synced snapshot through a computed path (a directory walk, or a file name built from a class name), it also shows the Upstream source of each class a changed file names in a string literal under that directory, or, when one does not fit, its declaration lines (`namespace`, `use` and the class or interface line with its `extends` and `implements`), as its heading says ([ESC-10.2-7](../escalations/ESC-10.2-7.md)). The test may reach the snapshot through a path constant it imports, such as `REPO`. It then also shows, first, the source of a class the test names itself and of a class whose method the test cites as `<Class>::<method>` (such as `Container::alias`, the method whose message the test asserts), then each file its directory walk selects by a `<name>.php` suffix (such as every `*ServiceProvider.php`). When one of these does not fit, its declaration lines come with the methods the test points at, the ones a regular expression in the test matches by declaration or the test cites, as its heading says ([ESC-10.4-2](../escalations/ESC-10.4-2.md)). All of it is shown within the prompt's size cap (evidence (h), [MAINT-2026-10-22-fidelity-whole-files](../../decisions/MAINT-2026-10-22-fidelity-whole-files.md)). A file it names without its text is shown in full in another section, or omitted for size, as its note says; such a file is not missing from the repository.

**Story scope.** The diff runs from the Story's base to its tree, so it can also hold other PRs that merged while the Story was open, each reviewed on its own. The prompt shows only the Story's own change: its manifest, the files in a path the Story may edit, and the test files declaring an Xaravel Test id its manifest assigns. Every other changed file is named under the diff as left out, and no evidence is drawn from it ([ESC-9.10-4](../escalations/ESC-9.10-4.md)). Evidence (e) likewise shows only the Story's own touched Xaravel Tests, and names any other touched test file ([ESC-9.10-3](../escalations/ESC-9.10-3.md)).

**Retrospective action items.** From Epic 9 on, a retrospective action item that changes `packages/**` is reviewed as a Story is ([MAINT-2026-10-16](../../decisions/MAINT-2026-10-16-unattended-orchestrator.md), amendment 2026-10-22). In place of a manifest, the prompt carries the item's sprint status entry under `## Action item`. Its scope is the paths a Story of each component the entry lists may edit. Its assigned Xaravel Test ids are those its own touched Xaravel Tests declare, so the Oracle fixtures of those tests are in the prompt as for a Story. Wherever the checklist says the Story, it means that item.

**Xaravel Tests.** The prompt shows each added or changed Xaravel Test in full, with every declaration it uses, directly or through another, from its own file or from a repository test module its file imports, each with its `path:lines`: the helpers it calls, including through a spread (`...helper()`), and the fixtures they name (evidence (e), [ESC-9.9-4](../escalations/ESC-9.9-4.md), [ESC-9.10-1](../escalations/ESC-9.10-1.md)).

An item is `n/a` only when the PR has nothing it applies to, such as F-10 on a PR that changes no Oracle request file.

### F-1: Assertions match Upstream

**Check.** Compare each changed or added Ported Test with its Upstream source lines, as the Inventory row's `source` gives them. Every Upstream assertion has a counterpart that checks the same subject against the same expected value, in the same order. It fails when an assertion checks something else, checks a different value, or is missing. It also fails when the Upstream source is unavailable and the PR adds or changes a Ported Test, because the match cannot be confirmed.

### F-2: No expected value is weakened

**Check.** Compare each expected value with Upstream's. It fails when an exact comparison becomes a looser one (`assertSame` to `assertEquals`, an exact string to a substring or a pattern, an exact count to a minimum), when an expected value is changed to match what Xaravel produces, or when an expected exception class or message is generalised. A change is allowed only when the line carries an `// adapted:DIV-<n>.<k>` marker whose clause permits exactly that change.

### F-3: No assertion is removed without a DIV clause

**Check.** Count the assertions of each Ported Test against Upstream's. It fails when an Upstream assertion has no counterpart and no `// adapted:DIV-<n>.<k>` marker cites a DIV clause that allows dropping it. A clause allows fewer assertions only when its record lists it in `fewer_assertions`.

### F-4: Every new Skip Reason is justified and its precedence is right

**Check.** For every Expectations line the PR sets to `skip`, the reason applies to that test: the named `deferred:` item, `blocked-by:<component>` Component, Non-Goal or `intentional-divergence:DIV-<n>` really covers it. When more than one reason could apply, the line records the one the [Precedence](../README.md#precedence) section of `conformance/README.md` puts first ([ESC-5.2-1](../escalations/ESC-5.2-1.md)): `upstream-skip`, then the reasons that keep the test in the SM-1 denominator, and only then the reasons that exclude it. When in doubt, the right reason is the one that counts against conformance. It fails on an unjustified reason or the wrong precedence.

### F-5: Every `adapted` marker matches its clause

**Check.** For every `// adapted:DIV-<n>.<k>` marker on an assertion, and every Expectations `adapted` field, read clause `DIV-<n>.<k>` in `decisions/DIV-<n>.md`. The adaptation is what that clause describes, and nothing more. It fails when the clause does not exist, when it covers a different construct, or when the code changes more than the clause allows.

### F-6: Every Oracle error fixture is the error Upstream's test expects

**Check.** For every Oracle fixture the Story relies on whose output is an error (`output.error` not null), the error is the one the Upstream test expects: the same exception class and, where the test checks it, the same message. The Inventory records only whether the test passed or failed on the Oracle (Epic 5 retro item 9), so an error fixture can stand for the wrong failure. It fails when an error fixture's error differs from the error the Upstream test expects.

### F-7: Every Xaravel Test verifies the consequence it declares

**Check.** For every added or changed `xaravelTest(id, consequence, …)`, the body checks what its consequence string declares, and each `FR-<n>.<k>` or `AD-<n>.<k>` token it cites names the bullet the test actually verifies ([ESC-5.9-1](../escalations/ESC-5.9-1.md)). It fails when the body checks less than the string claims, or when a cited bullet is not the one tested.

### F-8: No stub, fake or partial implementation of another Component

**Check.** The PR changes code only in its own Component. It fails when it adds a stub, a fake, a hard-coded return or a partial implementation of another Component's behaviour to make a test pass (FR-111.4). A test that needs a later Component is marked `blocked-by:<component>` instead.

### F-9: Every `@asyncRoot` tag is true

**Check.** Every `@asyncRoot` tag the PR adds or keeps is true, under AD-6's Derivation and Enforcement rules and DIV-1 ([ESC-9.1-4](../escalations/ESC-9.1-4.md)). AD-6 has two kinds of async method, each with its own tag:
- `@asyncRoot <Contract.method>` is true when the method really performs IO behind that async-root Driver contract method.
- `@asyncRoot callback` is true when the method is async only because it accepts a callback that DIV-1 allows to be async (AD-6's callback clause), as with `runCounted` and `runWithMockery` ([ESC-6.4-1](../escalations/ESC-6.4-1.md)), or when it is a contract method whose implementations are such callbacks, as with `ValidationRule::validate` ([ESC-10.2-6](../escalations/ESC-10.2-6.md)).

It fails when a tagged method neither does such IO nor accepts such a callback, when it only calls other async code it could have kept sync, or when a method that does such IO, or is async because of such a callback, has no tag. The check covers the tags the change keeps on the files it touches and the new exports it leaves untagged, not only the tags it adds ([ESC-9.2-2](../escalations/ESC-9.2-2.md)). A dual helper (AD-6's Dual helpers rule) is not async and takes no tag: it returns its callback's own type, `T` for a sync callback and `Promise<T>` for an async one, and never a declared Promise or thenable type. The Scope Frame runners `runInFrame`, `runInRootFrame` and `runInNarrowFrame` are dual helpers ([ESC-9.3-1](../escalations/ESC-9.3-1.md)).

### F-10: Oracle requests match the Upstream test's inputs

**Check.** For every request in a changed `conformance/oracle-requests/<story-id>.jsonl`, its `setup` and `exprs` are the inputs of the Upstream test its `id` names, or the request carries a recorded reason for the difference. A request must not get arbitrary PHP signed as an expected value (Epic 3 retro R4). It fails when `setup` or `exprs` differ from the Upstream test's inputs without a recorded reason.
